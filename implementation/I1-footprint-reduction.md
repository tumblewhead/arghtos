# I1 goal

Determine the smallest architecture-compatible implementation profile that still preserves the required scheduler behavior.

I1 is an experiment branch. It must not silently weaken proofs/contracts. Any feature or contract reduction must be recorded explicitly before it becomes canonical.

# Measurement rule

Every I1 change must report:

* host tests;
* sanitizer tests;
* portable-source boundary;
* Cortex-M23 compile;
* linked resident footprint;
* symbol-size delta;
* stack-usage/MSP delta;
* proof/contract impact.

The PR workflow is the executable evidence source.

# Reduction order

I1 will attack the largest sources of generality before instruction-level polishing.

## R1 - Remove runtime configuration generality

Hypothesis:

A build-time generated/static configuration can remove substantial validation/startup code while preserving the no-dynamic-allocation model.

Candidates:

* generated task table;
* stack regions allocated/generated by build tooling;
* compile-time task-count checks;
* no runtime pairwise overlap validation in production profile;
* no runtime descriptor class/priority validation in production profile;
* retain full validation in host/config-generation tooling.

Expected effect:

* reduce portable kernel code materially;
* small descriptor shrink opportunity;
* no scheduler-semantic change after startup.

Required proof review:

* P0 configuration validity moves from runtime proof evidence to build/generator evidence;
* P2 stack non-overlap becomes generator/linker evidence.

## R2 - Compress runtime diagnostic representation

Hypothesis:

Basic profiling can preserve its intent with smaller counters/packing.

Candidate experiment:

* keep 32-bit cumulative CPU time;
* reduce observed max-run width if a declared profiling quantum/range is acceptable;
* pack state/wake/age/missed-release fields;
* measure code cost of packing before adopting.

No change is accepted unless total footprint improves after the extra packing logic is linked.

## R3 - Reduce public/runtime misuse validation in production profile

Hypothesis:

The fully validated I0 release path carries significant code.

Possible profile split:

* host/debug profile keeps exhaustive misuse checks;
* minimum-footprint production profile treats violation of private/internal preconditions as fatal or unsupported;
* public invalid IDs/context checks retained where externally meaningful.

Any removed check must be listed explicitly and reviewed against C0-C10.

## R4 - Simplify API surface only if requirement-compatible

Candidates to measure separately, not assume:

* `sleep_for` as pure wrapper or optional convenience;
* task-context `wake` if interrupt wake is the only required activation source;
* profile snapshot surface versus direct compact diagnostic export.

Removing a required API requires contract approval and is not an implementation-only optimization.

## R5 - Cortex-M23 port compaction

Candidates:

* collapse tiny C wrappers into assembly when actually smaller;
* board timer hooks linked directly where safe;
* remove duplicate context/query helpers;
* compare C versus assembly service-call and special-register paths;
* keep the architecture-neutral port ABI unchanged.

## R6 - Instruction-level size work

Only after R1-R5:

* branch/switch shaping;
* helper folding;
* LTO;
* constant-width arithmetic;
* assembly compaction;
* call-graph restructuring.

# Stop condition

If a semantics-preserving compact profile remains materially above 1536 B after R1-R5, I1 should stop trying to win through micro-optimization and record the minimum measured feasible footprint.

At that point the project must choose among:

1. relax the soft footprint target;
2. reduce the default 32-task requirement;
3. reduce required diagnostics/profiling/API features;
4. adopt a more specialized generated scheduler architecture.

# Non-negotiable I1 invariants

Unless explicitly revised through contracts/proofs:

* no dynamic allocation;
* static/predeclared task set;
* protected periodic RMS domain;
* async starvation avoidance;
* preemption;
* PSP/MSP Cortex-M23 task/kernel split;
* wait/sleep/yield semantics;
* idempotent async wake;
* no lost wake at wait boundary;
* timer catch-up is bounded arithmetic;
* crash logging exists;
* all resident code/data counts;
* portable kernel remains target-independent.

# Correctness fixes discovered while resuming I0

## Cortex-M23 idle path

The checked-in I0 source contained a malformed inline-assembly string in `arghtos_port_idle_wait()`.

More importantly, the intended sequence contained:

```text
WFI
enable interrupts
...
WFI
disable interrupts
```

The second WFI can execute after a pending handler has already made work READY, putting the processor back to sleep while runnable work exists.

I1 replaces this with:

```text
PRIMASK already set by PendSV
DSB
WFI
CPSIE i
ISB
CPSID i
return to masked readiness check
```

No second WFI occurs after the pending handler gets a chance to run.

## First-dispatch MSP reclamation

I0 documentation stated that the startup MSP hardware frame was reclaimed before the first PSP task ran, but the assembly computed the adjusted MSP and never wrote it back.

I1 now restores:

```text
MSP = stacked_frame + 32 + optional_alignment_pad
```

where the optional four-byte pad is derived from stacked xPSR bit 9.

# Architectural lower-bound consequence

R1b total is:

```text
4004 B
```

The portable kernel bucket is 2706 B, but that bucket contains both executable code and the 652 B static kernel state:

```text
controls        640 B
static C9        12 B
---------------------
kernel state    652 B
```

Therefore the R1b footprint excluding portable kernel executable code is approximately:

```text
4004 - (2706 - 652) = 1950 B
```

That 1950 B consists of required scheduler state plus the current port, descriptors, crash record, linker metadata, and MSP estimate.

This is already:

```text
1950 - 1536 = 414 B
```

over the target before counting any portable scheduler executable code.

Thus **the 1.5 KiB target cannot be reached by portable-kernel code optimization alone**.

Even under the more generous thought experiment where all current port executable code disappeared, the retained metadata/state/MSP terms are approximately:

```text
controls                    640 B
static C9                    12 B
task descriptors            512 B
crash record                 64 B
ArghtOS-only MSP            104 B
linker metadata              16 B
--------------------------------
non-port-code lower bound  1348 B
```

That leaves only:

```text
1536 - 1348 = 188 B
```

for the entire portable scheduler plus context/port code.

Therefore the next checkpoint must attack representation/state size, not merely instruction count.

# R1 conclusion

R1 is successful as an experiment:

* R1a proved runtime configuration validation costs about 196 B in the first measured branch revision;
* R1b proved linked static ownership saves another 84 B in the same-revision comparison;
* R1b total is 4004 B;
* configuration generality is not the dominant remaining problem.

Proceed to R2: compact runtime/descriptor representation.
